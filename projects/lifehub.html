The project

Course foundation.
Personal direction.

LifeHUB was my individual project for the IN00DL12 Web Applications Fundamentals course, a 5-credit course completed with grade 5/5. A simple task list would have met the basic project requirement, but I expanded the scope during the course to include shopping, exercise and food tracking.

The course covered HTML and CSS development, JavaScript object-oriented principles, browser programming and asynchronous calls. LifeHUB brings those foundations together in a ToDo list, shopping list, exercise tracking and food logging tool.

Course context

Web foundations.
Personal product.

The original course goal was to build a website with HTML and CSS, browser programs with JavaScript and asynchronous calls from the browser.

The assignment provided room to choose the implementation scope. I used the course to practise a larger interface with several connected feature areas, local browser storage and external weather data.

Technical implementation

A browser app with
an operations mindset.

LifeHUB is a client-side application, but the implementation still required the same questions that matter in larger systems: where state lives, how external data fails, how the interface behaves on different devices and how the application can be run and tested consistently.

The application is built with HTML, CSS and JavaScript. Its dashboard and feature views share browser-side logic, localStorage-backed data and reusable interaction patterns. Open-Meteo is integrated asynchronously for weather data, while the UI is designed around mobile gestures, touch targets and clear feedback.

For local development, the project runs through a static HTTP server instead of relying on file:// browser behaviour. During implementation, I used browser testing, debugging, refactoring and AI-assisted review while remaining responsible for the final code and decisions.

Technical limitations and next steps

A useful prototype,
with clear boundaries.

The current implementation is a browser project. Its limits also make the next engineering steps clear.

01

Browser storage

Data is stored in separate localStorage keys for tasks, shopping, exercise and food tracking. This makes the state easy to inspect but ties it to one browser and origin.

02

External data

Weather data is fetched asynchronously from Open-Meteo. Network and data errors are limited and the interface would benefit from a more useful visible error state.

03

Data portability

The application has no export, import or backup feature. Moving to another browser or phone therefore requires manual access to browser storage.

04

Next version

A future version would add visible error states, data export and import, automated tests and a proper Android implementation with more suitable touch interaction and persistence.
